# Triggers

Moved verbatim from AGENTS.md; served by `editor_help topic=triggers`.

- `editor_triggers` structured support is strictly verified TR v12 single Always/CodeSnippet controller. Local patch requires new output/confirmWrite; apply requires confirmDestructive and retains original backup/round-trip files. Unknown shapes refuse; serialization equality is not XS compilation/effect proof.
- Native `uiLoadTriggers` / `uiSaveTriggers` / `saveScenario` receive filename stems, not suffixed filenames: game appends `.trg` / `.mythscn`. Raw trigger import/export require confirmDestructive. Unknown structured original triggers need separately authorized native backup restoration; helper apply does not guess their shapes.

## Related tools added later

- `editor_trigger_edit`: edits on the same trigger in one batch are merged (original numbering); only real conflicts refuse. `outputPath:"auto"` writes `<stem>.eN.trg`; the result's `next {path, expectedSha256}` chains the next edit. CodeSnippet replacements (ValueType 72) may be long and multi-line.
- `editor_trigger_elements` looks up the condition/effect catalog and lists byte-copy exemplars (use `duplicates`/`copyEffects`); creating elements from the catalog is not supported (binary layout unproven). `library=true` adds exemplars from shipped TR v12 campaign scenarios (index built by `editor_generate_catalog`; each location has `sourcePath`, `sourceSha256`, triggerId/triggerName, elementIndex) and `encodingProven` per parameter vartype; TR v11 scenarios are not indexed. Census details: `research/TRIGGER-CORPUS.md`.
- Cross-file copy (effects only): a `copyEffects` entry with `sourcePath` + `sourceSha256` copies from another `.trg` or a game-written TR v12 `.mythscn` (`sourceTriggerId`/`expectedSourceName`/`effectIndex` = the library location's triggerId/triggerName/elementIndex). `copyValues [{copyHandle, parameter, expected, value}]` then sets single-value parameters of the copy (e.g. `PlayerID`, `Message`) when the index proves that value type re-encodes byte-exact (`UNPROVEN_VARTYPE` otherwise; unit lists use `objectReplacements` with `copyHandle`). A TR v11 source fails `UNSUPPORTED_SOURCE`; a copied `Trigger:` element must get its `EventID` set via `copyValues`. Warnings flag source string keys (`{STR_...}`) the target mod may lack. Example: copy `Chat: Send Chat` from `campaign\om\om09.mythscn` (trigger 647, element 1) and set `PlayerID=1`, `Message="..."`; preview `renderedXs` shows `trChatSend(1, "...");`. Proof stays `editor_triggers apply` + playtest (live 2026-10-13: this exact copy into a scratch export, applied with `autoBackup` and `scripts="restore"`, showed the chat line at game start).
- Bulky readers accept `fields` and `saveTo` (new .json path); results over 16 KB carry a `truncationHint`.

## Backups on apply

`editor_triggers apply` exports a game-written `before-trigger-import` backup (moved, hash-verified, to active-profile `<id>\trigger_backup`), imports, then round-trips and compares. Two ways to pin the original:

- Reviewed: pass `expectedLivePath` + `expectedLiveSha256` (a live export you inspected); the backup must match it semantically.
- `autoBackup=true`: omit both. The host takes the game-written export immediately before the import, retains it, and returns `backupPath`/`backupSha256`. Only `expectedSha256` of the prepared file stays required; passing `expectedLive*` together with `autoBackup` is refused. It trades the human-reviewed live export for convenience; the retained backup is the restore source (apply it back with `autoBackup=true` too). Live-verified: apply and restore of an empty set round-tripped exactly.
- Lost-update check for `autoBackup`: every `editor_trigger_edit` result carries `basePath`/`baseSha256` (the export the chain of edits started from; pass `next` on unchanged when chaining). Give them to apply as `expectedBasePath`/`expectedBaseSha256`: if the fresh backup differs from the base (someone edited triggers in the editor after the export), apply refuses with `LIVE_SOURCE_CHANGED` listing the differing triggers and imports nothing (`lostUpdateCheck:"verified"` on success). Without them the result says `lostUpdateCheck:"skipped"`. Not live-tested yet; the comparison is fixture-tested.
  - Lost-update check (offline fixture-tested, not yet live): every `editor_trigger_edit` result carries `basePath`/`baseSha256` (the export the chain started from; pass `next.basePath`/`next.baseSha256` on with each chained edit). Give them to apply as `expectedBasePath`/`expectedBaseSha256`: if the fresh backup is not trigger-equivalent to the base (someone edited triggers in the editor since the export), apply fails with `LIVE_SOURCE_CHANGED` listing added/removed/changed triggers and imports nothing; the backup holds the newer live set. Without them the result says `lostUpdateCheck:"skipped"`.

## Code through parameters (injection guard)

The game expands each element's template (condition `command`, effect `expression`) into `trigtemp.xs`. String parameters sit inside quotes (`trQuestVarGet("%QVName%")`) and the game escapes quotes in them (`\"`), so code injected through QVName/ProtoUnit/... breaks the compile of every trigger. `editor_trigger_edit` refuses such values (`STRING_PARAM_NOT_CODE`). Bare-code slots such as `Op` accept code characters only with top-level `allowRawXsInjection=true` (otherwise `RAW_XS_INJECTION`), and the result then warns. The supported way to run code is an `XS: Code Snippet` effect: copy one (copyEffects/duplicates) and set `CodeSnippet`. Every result carries `renderedXs` per touched element (templates with stored values, approximate) with a brace/quote balance check; after a playtest, `editor_xs_diagnostics operation=trigtemp` is the proof.

## XS Scripts list is reset by apply

The scenario's Triggers -> XS Scripts list (external `.xs` files such as `om10\om10_diffbonus.xs` whose functions Code Snippets call) is not part of the `.trg` format, and importing triggers resets it. Functions from those scripts then stop compiling, and the triggers using them fail silently (observed: no chat, timers not moving). `editor_triggers` inspect/validate/apply return `xsScripts.lastKnown`: the union of the `include` lines in `trigger\trigtemp.xs` (the last trigger compile) and the TR scripts of the newest save in the profile scenario folder, each with its source. After apply, re-add every name in Triggers -> XS Scripts, save, then run `editor_xs_check scenarioPath="latest"` to confirm every script resolves.

When `lastKnown` is non-empty, apply refuses unless `scripts` is `"restore"` or `"ignore"` (re-add by hand). `editor_triggers apply scripts="restore"` does the re-add itself: it reads the Script Manager list before the import, applies, then includes again every `lastKnown` name that matched a listed row and verifies the list by OCR (`scriptRestore`). Listed rows without an exact `lastKnown` source name are reported as `unrestorable`; OCR text is never typed back. `editor_xs_scripts` lists, verifies (complete expected list), includes and removes names directly. Both work on the normal and the alternative UI at 2560x1440 (live 2026-10-14 for the alternative one: list, include, remove, verify, apply restore); other client sizes, moved windows and the alternative UI at 1920x1080 are refused or untested. The alternative Script Manager has no name field: include presses its Add Script button, types into the "New Script Name" popup and clicks the confirm button; its list clips long names, so rows match by their start, `verify` reports `prefixMatched` instead of `verified`, and include steps report `fullNameVerified:false`. Live 2026-10-13: the import emptied the list and restore re-included `om10\om10_diffbonus.xs`. The editor accepts names that do not exist, so check `resolution` / `editor_xs_check`. Save the scenario to keep the list.

## Where trigger scripts resolve; merging import

- Play compiles `trigger\trigtemp.xs`, whose `include` lines name the XS Scripts list entries. Live 2026-10-13: `om10\om10_diffbonus.xs`, present only under the **enabled** subscribed mod's `trigger\` folder, compiled; a name found nowhere failed with a Trigger Error dialog `XS: Error 0123: failed to open file`. `editor_xs_scripts` `resolution` checks profile `trigger\`, then enabled mods from `mods\myth-mod-status.json` (`from:"mod"`), then the stock archive. Disabled mods and precedence between copies are untested.
- The editor's own Import (`editor_uiImportTriggers`, the "Load Menu" file browser with Import Cameras / Import Units toggles) **merges**: it appends the file's triggers (a duplicate name got suffix `1`) and keeps the XS Scripts list. `editor_triggers apply` replaces the whole set and resets the list. No host tool drives the Load Menu yet (live 2026-10-13, normal UI only).
